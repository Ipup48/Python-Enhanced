ถอดรหัสวิธีคิดของคนสำเร็จ:

  • รวมการเข้าถึงข้อมูลไว้หลัง “สัญญา” (ABC) เดียว — Repository Pattern
  • ซ่อนโครงสร้างภายใน และไม่คืนของที่ภายนอกแก้ไขได้ (Information Hiding)
  • ห่อ “เทคโนโลยีที่เปลี่ยนบ่อย” ด้วย abstraction ที่มั่นคง (Protected Variations)
  • แยก Entity (มีตัวตนด้วย id) ออกจาก Value Object (เทียบด้วยค่า) ให้ชัดเจน

Finding Sandbox: ห้องนิรภัยที่ประตูเปิดทิ้งไว้

ทัศนคติประจำใบงาน: Failure is learning — ผิดหรือถูกไม่สำคัญ นี่คือการทดลองเพื่อเติบโต

พิจารณาโค้ดต่อไปนี้ แล้วสังเกตว่า “ข้อมูลภายใน” รั่วไหลได้อย่างไร

class Student:
    def __init__(self, id: int, email: str):
        self.id = id
        self.email = email


class StudentStore:
    def __init__(self):
        self._students: dict[int, Student] = {}

    def add(self, s: Student) -> None:
        self._students[s.id] = s

    def all(self) -> dict[int, Student]:
        return self._students   # คืนโครงสร้างภายในโดยตรง!


store = StudentStore()
store.add(Student(680001, 'student@example.ac.th'))

data = store.all()
data[680001].email = 'hack@evil.com'   # ข้อมูลจริงพัง!
print(store.all()[680001].email)

1) เหตุใดการแก้ข้อมูลใน data จึงส่งผลถึงข้อมูลภายใน store ทั้งที่ _students ขึ้นต้นด้วย underscore

ผลลัพธ์: อีเมลเปลี่ยนเป็น 'hack@evil.com'
เหตุผล: เพราะ all() คืนค่า Reference ของ dict ตรงๆ ไม่ใช่สำเนา และ _ เป็นเพียง Naming Convention เท่านั้น

2) คุณจะออกแบบ all() และตัว Entity อย่างไรให้ “คนภายนอกแก้ไขข้อมูลภายในไม่ได้เลย”

ออกแบบ all(): คืนค่าเป็น List สำเนาใหม่ด้วย list(self._students.values())
ออกแบบ Entity: กำหนดให้ Student เป็น @dataclass(frozen=True) เพื่อป้องกันการแก้ไข attribute

3) ลองให้ AI เสนอวิธีป้องกันการแก้ไขข้อมูลภายในมา 3 วิธี แล้วถกกับเพื่อน: วิธีใดน่าเชื่อถือที่สุด และคำตอบของ AI เชื่อถือได้มากน้อยเพียงใด (ฟังเพื่อนให้จบก่อนสรุปนะ)

3 วิธี: 1. คืนค่าสำเนา List 2. ใช้ @dataclass(frozen=True) 3. ใช้ MappingProxyType หรือ Read-only Tuple
ความน่าเชื่อถือ: น่าเชื่อถือสูงเพราะสอดคล้องกับหลัก Encapsulation และ Information Hiding
📦 กล่องความรู้เสริม (อ่านเฉพาะเมื่อจำเป็น):
  • Repository Pattern: รวมการเข้าถึงข้อมูลไว้หลัง “สัญญา” (ABC) ทำให้ Use Case ไม่ต้องรู้จักเทคโนโลยีการจัดเก็บ
  • DIP: Use Case พึ่งพา abstraction (UserRepository) ไม่ใช่ implementation
  • Information Hiding: ซ่อนโครงสร้างภายใน (private dict) และคืน “สำเนา” เพื่อป้องกันภายนอกแก้ไข
  • Protected Variations: ห่อหุ้ม “เทคโนโลยีจัดเก็บ” (จุดที่เปลี่ยนบ่อย) ด้วย ABC ที่มั่นคง
  • Entity vs Value Object: Entity มี identity (id) เช่น User; Value Object เทียบด้วยค่าและมัก immutable เช่น Email
  • frozen dataclass: @dataclass(frozen=True) ทำให้แก้ไขฟิลด์หลังสร้างไม่ได้ (FrozenInstanceError)

ส่วนที่ 1: อ่านแผนภาพแล้วตอบคำถาม (10 คะแนน)

1) «ABC» UserRepository ทำหน้าที่อะไรในระบบ และเหตุใดต้องแยก “สัญญา” ออกจาก implementation 2 คะแนน

ทำหน้าที่: เป็น Interface/Abstract Class กำหนดสัญญาการเข้าถึงและจัดการข้อมูลผู้ใช้
เหตุผลที่แยก: เพื่อลด Coupling ช่วยให้สลับเปลี่ยนเทคโนโลยีจัดเก็บข้อมูล (เช่น MySQL, Mongo) ได้โดยไม่กระทบ Use Case

2) ลูกศร “implements” จาก InMemoryUserRepository ชี้ไปยัง UserRepository หมายถึงอะไรในเชิงโค้ด Python 2 คะแนน

หมายถึง: InMemoryUserRepository สืบทอดคลาส UserRepository (Inheritance)
ในเชิงโค้ด: ต้อง Implement เมธอด abstract ทั้งหมด (save, find_by_id, all) ตามที่สัญญากำหนดไว้ให้ครบถ้วน

3) «dataclass frozen» ที่กำกับคลาส User หมายความว่าอย่างไร และ User จัดเป็น Entity ต่างจาก Value Object อย่างไร 2 คะแนน

dataclass frozen: วัตถุที่สร้างขึ้นจะเป็น Immutable ไม่สามารถแก้ไขค่า Attribute ภายนอกได้
ความต่าง: User เป็น Entity เพราะมี id ระบุตัวตน (Identity) ในขณะที่ Value Object วัดกันที่ค่าของข้อมูลและไม่มี identity

4) เมธอด find_by_id คืนค่าเป็น “User or None” การคืน None สื่อความหมายว่าอย่างไร 1 คะแนน

สื่อถึง: การค้นหาไม่พบข้อมูลผู้ใช้ที่ตรงกับ id ที่ระบุไว้ในระบบ

5) ลูกศร “stores” จาก InMemoryUserRepository ไปยัง User หมายถึงอะไร และใช้โครงสร้างข้อมูลใดในการเก็บ 1 คะแนน

หมายถึง: InMemoryUserRepository ทำหน้าที่จัดเก็บและดูแลวัตถุ User โดยใช้โครงสร้างข้อมูล dictionary (_users)

6) หากในอนาคตต้องการเปลี่ยนไปเก็บข้อมูลในฐานข้อมูล MySQL โค้ดส่วนใดต้องเปลี่ยนแปลงบ้าง 2 คะแนน

โค้ดที่ต้องเปลี่ยน: สร้างคลาสใหม่ เช่น MySQLUserRepository ที่สืบทอด UserRepository
ส่วนที่ไม่ต้องเปลี่ยน: คลาส User, UserRepository และ Use Case หลักภายนอกไม่ต้องแก้ไขเลย

ส่วนที่ 2: วิเคราะห์โค้ด (10 คะแนน)

from abc import ABC, abstractmethod
from dataclasses import dataclass


@dataclass(frozen=True)
class User:
    id: int
    email: str


class UserRepository(ABC):
    @abstractmethod
    def save(self, user: User) -> None: ...

    @abstractmethod
    def find_by_id(self, user_id: int) -> User | None: ...

    @abstractmethod
    def all(self) -> list[User]: ...


class InMemoryUserRepository(UserRepository):
    def __init__(self):
        self._users: dict[int, User] = {}

    def save(self, user: User) -> None:
        self._users[user.id] = user

    def find_by_id(self, user_id: int) -> User | None:
        return self._users.get(user_id)

    def all(self) -> list[User]:
        return list(self._users.values())


repo = InMemoryUserRepository()
repo.save(User(680001, "student@example.ac.th"))
repo.save(User(680002, "student2@example.ac.th"))

student = repo.find_by_id(680001)
print(student)
print(f"จำนวนนักศึกษาทั้งหมด: {len(repo.all())} คน")

1) เหตุใดเมธอด all() จึงใช้ list(self._users.values()) แทนการคืนโครงสร้างภายในโดยตรง ป้องกันความเสี่ยงใด 3 คะแนน

เหตุผล: เป็นการสร้าง List สำเนาใหม่ ไม่ส่ง Pointer/Reference ของ _users ออกไปภายนอก
ป้องกันความเสี่ยง: ป้องกันภายนอกแอบแก้ไข ลบ หรือเปลี่ยนแปลงข้อมูล dict หลักภายในคลาส Repository

2) การเรียก repo.find_by_id(999999) ให้ผลลัพธ์เป็นอะไร และโค้ดบรรทัดใดรับผิดชอบ 2 คะแนน

ผลลัพธ์: None
บรรทัดที่รับผิดชอบ: return self._users.get(user_id) (เพราะ get คืน None เมื่อไม่พบ key)

3) หาก save ผู้ใช้ที่มี id ซ้ำกับข้อมูลเดิมจะเกิดอะไรขึ้น เพราะเหตุใด 3 คะแนน

ผลที่เกิดขึ้น: ข้อมูล User เดิมในระบบจะถูกเขียนทับ (Update) ด้วย User ใหม่ทันที
เหตุผล: Dict ใน Python หากระบุ Key ซ้ำ ค่าของ Key นั้นจะถูก Update ด้วย Value ล่าสุด

4) หากพยายามแก้ไข user.email หลังสร้างวัตถุแล้วจะเกิดอะไรขึ้น เพราะเหตุใดจึงออกแบบเป็น frozen 2 คะแนน

ผลที่เกิดขึ้น: เกิดข้อผิดพลาด FrozenInstanceError
เหตุผลที่ออกแบบ: เพื่อสร้าง Immutability รับประกันความถูกต้องของข้อมูล Entity ไม่ให้ถูกแอบแก้ไขภายนอก

ส่วนที่ 5: สะท้อนคิดเชิงออกแบบ OOAD (6 คะแนน)

1) Repository Pattern ช่วยลด coupling ระหว่าง Use Case กับเทคโนโลยีการจัดเก็บข้อมูลอย่างไร 2 คะแนน

ทำให้ Use Case เรียกใช้งานผ่าน Abstract Class (UserRepository) โดยไม่จำเป็นต้องรู้รายละเอียดเชิงลึกของการจัดเก็บจริง

2) “จุดที่เปลี่ยนแปลง” ในข้อนี้คืออะไร และการออกแบบนี้ปกป้องระบบด้วย Protected Variations อย่างไร 2 คะแนน

จุดเปลี่ยนแปลง: เทคโนโลยีการจัดเก็บข้อมูล (dict, MySQL, MongoDB)
การปกป้อง: ใช้ ABC ซ่อนรายละเอียดของ Storage เมื่อเปลี่ยนเทคโนโลยีจึงไม่กระทบส่วนอื่น

3) เมื่อต้องเขียน Unit Test ให้ RegisterUserService ABC UserRepository ช่วยให้การทดสอบง่ายขึ้นอย่างไร 2 คะแนน

ช่วยให้สามารถ Mock หรือสร้าง InMemoryUserRepository สำหรับทดสอบได้ทันที โดยไม่ต้องเชื่อมต่อ Database จริง

จุดระเบิดเวลา: โค้ดส่วนที่เขียน SQL Query หรือต่อกับ API โดยตรงในชั้น Business Logic
วิธีห่อ: สร้าง Interface ABC ครอบไว้ แล้วย้ายโค้ดติดต่อ DB ไปไว้ในคลาส Implementation แทน

2) เขียน commitments สั้น ๆ 2 ข้อ เกี่ยวกับนิสัย “ไม่คืนโครงสร้างภายในให้ภายนอก” ที่คุณจะนำไปใช้จริง

1. จะคืนค่าเฉพาะ Copy หรือ Immutable Data ออกไปภายนอกคลาสเสมอ
2. จะออกแบบคลาสโดยซ่อน Attribute ภายในและให้เข้าถึงผ่าน Method ที่สัญญากำหนดไว้เท่านั้น
🪞 มุมสะท้อนคิดของโค้ช:

ชมความพยายามของตัวเอง 1 เรื่อง แล้วบันทึก “คำถามที่ยังค้างอยู่ในหัวคุณ” เกี่ยวกับ Repository หรือการปกป้องข้อมูล

ภูมิใจในตัวเองที่ทำความเข้าใจการแยก Abstraction ออกจาก Implementation และเห็นภาพความปลอดภัยของข้อมูลชัดเจนขึ้น
คำถามที่ยังค้างอยู่: ในระบบขนาดใหญ่ การจัดการ Transaction (เช่น Commit/Rollback) ผ่าน Repository Pattern ควรออกแบบร่วมกับ Unit of Work อย่างไร
